# Cross-System Patterns

<!-- nav:start -->
**[Index](README.md)** · [Kafka 00 Overview](kafka-00-overview.md) · Sibling catalogues: [Cassandra](../cassandra/patterns.md) · [Kubernetes](../kubernetes/patterns.md)

A running catalogue of recurring distributed-systems patterns, the mechanism behind each, and which studied systems use it. Seeded from the Kubernetes deep dives (`systems/kubernetes-*.md`) and extended with the Kafka series (`systems/kafka-*.md`); extend a row rather than adding a duplicate pattern when a new system is added.

**Systems covered so far:** Kubernetes (all subsystems), etcd, Apache Kafka 4.3 (all subsystems, including KRaft). Entries under *Elsewhere* for systems not yet deep-dived are pointers for future reports, not verified findings from this project.

**How to read the Kafka column.** Kafka is the most useful comparison partner Kubernetes has, because the two systems make *opposite* choices on several axes while agreeing on others — and the disagreements are almost always explained by one thing: Kubernetes is a control plane with no data plane of its own, while Kafka is a data plane that grew a control plane. A "—" means the pattern genuinely has no Kafka analogue, which is often the most interesting cell in the row.

## 1. Consensus and replication

| Pattern | Mechanism | In Kubernetes | In Kafka | Elsewhere |
|---|---|---|---|---|
| **Raft consensus** | Leader-based log replication; entries committed once a quorum acks; leader elected by randomized timeouts | etcd — the entire cluster state sits behind one Raft group (K8s [report 01](../kubernetes/kubernetes-01-apiserver-etcd.md)) | KRaft: `__cluster_metadata`, one Raft group for cluster metadata only (Kafka [report 03](kafka-03-kraft-controller.md)). **Deliberately not textbook Raft** — replication is *pull*-based (`Fetch`/`FetchSnapshot`), the leader never pushes, and pre-vote (KIP-996) exists to stop a partitioned voter disrupting a healthy leader | Consul, TiKV, CockroachDB, Spanner (Paxos per split) |
| **Quorum reads (ReadIndex)** | Leader confirms it is still leader before serving a read, avoiding a log write | etcd linearizable reads; kube-apiserver when `resourceVersion=""` | **No equivalent, by design.** Data reads go to the partition leader and are capped at the high watermark, which is itself the "replicated to a quorum-equivalent" marker. Brokers observing `__cluster_metadata` read only committed records. Kafka moves the quorum check to *write* time and never pays it on reads | Consul consistent reads, ZooKeeper `sync()`, Spanner TrueTime reads |
| **Single Raft group as a scaling ceiling** | All writes serialize through one leader; capacity is one node's fsync throughput | etcd, hence the 5,000-node envelope; mitigated only by splitting Events onto a second etcd | **Kafka is the system that does both.** Metadata is one Raft group with the same ceiling; *data* is sharded into per-partition leader/ISR groups with independent leaders. The lesson is that the ceiling is survivable when the hot path does not cross it — brokers never write to `__cluster_metadata` on the data path | Spanner, CockroachDB, TiKV shard into many Raft groups |
| **Leader election as an optimisation, not a lock** | Lease renewed before expiry; no fencing token validated by the guarded resource | `coordination.k8s.io/Lease`; a stalled leader can still write (K8s [report 02](../kubernetes/kubernetes-02-controllers.md)). Kubernetes relies on idempotence instead | **The direct counter-example, and the answer to this file's long-standing open question.** Kafka *does* issue fencing tokens and *does* validate them at the resource: the **leader epoch** is carried on every follower `Fetch` and rejected as `FENCED_LEADER_EPOCH`, the **partition epoch** rejects stale `AlterPartition`, and the **producer epoch** fences zombie transactional producers (`ProducerFenced`). A stalled Kafka leader that wakes up cannot write | Chubby and ZooKeeper issue fencing tokens; HDFS NameNode uses epoch numbers |
| **Epoch-based divergence detection** | On rejoining, a replica asks the leader where their histories diverged rather than assuming a truncation point | — (Kubernetes has no replicated per-object log to diverge) | **KIP-101**: the leader-epoch checkpoint file plus the `OffsetsForLeaderEpoch` RPC. Before it, followers truncated to the high watermark, which silently lost data in one failure ordering and left replicas *permanently divergent* in another. KIP-320 extends the same check to consumers (Kafka [report 02](kafka-02-replication-isr.md)) | Raft's `prevLogIndex`/`prevLogTerm` consistency check; Git merge-base |

**Key judgement.** Kubernetes accepted a single-Raft-group ceiling in exchange for a strictly serialisable, watchable, whole-cluster keyspace. Kafka accepted the same ceiling *for metadata only* and sharded the data plane beneath it. Both bets are defensible; the difference is that Kafka's hot path never touches consensus, so its Raft group sizes for *metadata churn* rather than for workload throughput.

## 2. Storage engines and on-disk structures

| Pattern | Mechanism | In Kubernetes | In Kafka | Elsewhere |
|---|---|---|---|---|
| **Write-ahead log** | Append durably, then apply to the in-memory/paged structure; replay on restart | etcd WAL, fsynced before Raft commit | **Kafka is the degenerate, and therefore purest, case: the log has nothing to apply *to*.** There is no downstream structure — the WAL is the product. Every other system's WAL is an implementation detail; Kafka's is the API. Streams inverts this again: changelog topics are the WAL for RocksDB state stores | Postgres WAL, Cassandra commitlog, InnoDB redo, RocksDB WAL |
| **B+tree page store** | Copy-on-write B+tree with a freelist; random reads cheap, writes amplify | etcd's bbolt; fragmentation needs `defrag` | **Not used.** Lookup is a **sparse, memory-mapped offset index** — one entry per `log.index.interval.bytes`, binary-searched, then a linear scan. Sparse because dense indexing would cost more page cache than it saves (Kafka [report 01](kafka-01-log-storage.md)) | Postgres/InnoDB heaps and indexes |
| **LSM tree** | Buffer writes in memtables, flush to sorted files, compact in background | *Not used by etcd* — a notable divergence | Not used for the log — there is nothing to sort, since offsets arrive in order. **But Kafka Streams state stores are RocksDB**, so an LSM sits one layer up, with its durability delegated back down to a Kafka changelog topic (Kafka [report 07](kafka-07-streams-connect.md)) | RocksDB, Cassandra, HBase, ScyllaDB, TiKV, BigTable |
| **MVCC with a monotonic revision** | Every mutation gets a global revision; old versions readable until compacted | etcd revisions, exposed to clients as `resourceVersion`; the watch protocol depends on them | **The offset is the same idea with a crucial difference: it is a position, not a version.** Offsets are per-partition (not global), monotonic, and dense; there is no "read key K as of offset N". Compacted topics approximate last-value-per-key, which is the closest Kafka gets to a versioned store | Postgres xmin/xmax, Spanner timestamps, CockroachDB MVCC |
| **Compaction vs reclamation as separate steps** | Logical version removal ≠ physical space return | etcd `compact` then `defrag`; forgetting the second causes `database space exceeded` | **A terminology trap worth naming explicitly.** Kafka's "compaction" is not etcd's or an LSM's: `cleanup.policy=compact` means *retain the latest record per key* (the `LogCleaner`, an `OffsetMap`, a dirty-ratio trigger), while `cleanup.policy=delete` is time/size retention. They are orthogonal and can both be on. Physical reclamation is the `.deleted` rename plus `log.segment.delete.delay.ms` | Postgres VACUUM vs VACUUM FULL; Cassandra tombstones vs compaction |
| **Tombstones with a delete horizon** | A deletion is itself a record, retained long enough for every reader to observe it | — | A null-valued record in a compacted topic; retained for `delete.retention.ms` past the **delete horizon** so consumers and standby replicas cannot miss the delete and resurrect the key (Kafka [report 01](kafka-01-log-storage.md)) | Cassandra tombstones + `gc_grace_seconds`; CRDT tombstones |
| **Hard size quota with an alarm** | Refuse writes rather than degrade unboundedly | etcd `--quota-backend-bytes`, 2 GiB default, NOSPACE alarm makes the cluster read-only | Kafka does **not** do this: retention (`retention.ms`/`retention.bytes`) bounds size continuously instead, so there is no cliff to hit — until there is. A full log dir takes the **directory offline**, and every partition it hosted goes offline with it, which is a far larger blast radius than etcd's read-only alarm | S3 bucket quotas; few systems fail as hard as etcd |
| **Two-tier storage with a continuous address space** | Cold data moves to cheaper storage without changing how it is addressed | — | **KIP-405 tiered storage**: `local.retention.*` bounds the local log, `RemoteLogManager` copies segments to an object store, and the offset space stays continuous across the boundary. Only the fetch path changes — and it loses zero-copy when it crosses (Kafka [report 01](kafka-01-log-storage.md)) | Snowflake/BigQuery storage-compute split; S3 Glacier tiering; HDFS heterogeneous storage |

## 3. Control and coordination

| Pattern | Mechanism | In Kubernetes | In Kafka | Elsewhere |
|---|---|---|---|---|
| **Level-triggered reconciliation** | Act on current observed state, not the delivered event; loops are idempotent and convergent | The core model — every controller, kubelet syncLoop, kube-proxy rule sync | **In the control plane only, and this is the boundary the file's open question asked about.** Brokers replay `__cluster_metadata` into `KRaftMetadataCache` and reconcile reality against it (start/stop fetchers, become leader). The **data plane is strictly edge-triggered and offset-ordered** — a consumer that "reconciled to current state" would have skipped records. The boundary is exactly control plane vs data plane, and it is not a coincidence: level-triggered requires cheap full-state reads, which a 30-day log does not offer | Terraform, ArgoCD, Chef/Puppet. Contrast: Airflow, Step Functions |
| **Declarative desired state + observed status** | Split one object into intent (user-owned) and reality (controller-owned) | Every object; `metadata.generation` vs `status.observedGeneration` | `PartitionRecord`'s assigned replicas are the intent; the **ISR is the observed status**, written back by the *leader* via `AlterPartition` and accepted by the controller only if the partition epoch matches. Same split, opposite direction of travel: in Kafka the data-plane node reports status upward | Crossplane, Cluster API, Config Connector |
| **Optimistic concurrency control** | Compare-and-swap on a version; retry on conflict; never lock | `resourceVersion` on every write; etcd `Txn` with `ModRevision`; HTTP 409 | Epoch comparison everywhere: partition epoch on `AlterPartition`, leader epoch on `Fetch`, producer epoch on `Produce`, member epoch on `ConsumerGroupHeartbeat`. Same pattern, but Kafka's version *is* the fencing token (see §1) | DynamoDB conditional writes, S3 preconditions, Git refs |
| **Watch + resume token** | Long-lived change stream keyed by a position, plus a defined "you fell behind" error | Kubernetes watch with `resourceVersion`; `410 Gone / too old resource version` forces a relist | **The archetype the others imitate.** A consumer offset is the resume token; `OffsetOutOfRange` is `410 Gone`; `auto.offset.reset` is the relist policy. The difference is scale of the window: Kubernetes keeps ~10² events in RAM, Kafka keeps days of data on disk, which is why Kafka consumers rarely fall off the end | MongoDB change streams, DynamoDB Streams, Postgres replication slots |
| **Bounded history buffer** | Keep a fixed window of recent changes so slow readers can catch up | apiserver watch cache ring buffer (100 → 102,400 entries) | **Retention is the same pattern with three more orders of magnitude and a different medium** — hours to days, on disk, not a RAM ring. This single quantitative difference is why Kafka can be a system of record and the watch cache cannot | Redis replication backlog; CDN origin buffers |
| **Expectations / in-flight accounting** | Record what was just issued so it is not re-issued before the cache catches up | `UIDTrackingControllerExpectations` in the ReplicaSet controller | The producer's in-flight sequence numbers, matched broker-side by `ProducerStateManager`'s **5-batch-per-producer** cache — which is precisely why `max.in.flight.requests.per.connection` must be ≤ 5 for idempotence to survive a retry (Kafka [report 04](kafka-04-producer.md)) | TCP's in-flight window; actor outstanding-request tables |
| **Deferred commit over speculative state** | Compute against uncommitted state, publish only on commit, roll back wholesale on failure | Scheduler `AssumePod` / `Unreserve` (a narrow instance) | **`QuorumController` is the strongest example in either system.** It replays records into `TimelineHashMap`/`TimelineObject` *before* Raft commits them, parks client futures in an offset-keyed `DeferredEventQueue`, and on lost leadership discards everything with one `snapshotRegistry.revertToSnapshot(lastStableOffset)`. Snapshot epochs are literally log offsets (Kafka [report 03](kafka-03-kraft-controller.md)) | Database MVCC snapshots; STM; speculative execution |

## 4. Caching and staleness

| Pattern | Mechanism | In Kubernetes | In Kafka | Elsewhere |
|---|---|---|---|---|
| **Read-through cache in front of the datastore** | One reader populates a shared cache; many consumers served from RAM | apiserver watch cache — one reflector, thousands of watchers | **The OS page cache, and nothing else.** Kafka deliberately has no application-level block cache: no duplicate copies, no GC pressure, and `sendfile` can serve straight from it. The cost is that Kafka's most important performance property is invisible to the JVM and untunable by config — "add RAM" beats every setting | CDN origin shielding; DB read replicas |
| **Client-side replicated cache** | Every consumer maintains a full local mirror via list+watch | client-go informers in every controller, kubelet, kube-proxy | `KRaftMetadataCache` on every broker, built by `MetadataLoader` replaying `__cluster_metadata` — a full mirror maintained by the same log-replication machinery. Clients keep a smaller `Metadata` mirror refreshed on `metadata.max.age.ms` | Envoy xDS state-of-the-world; Consul agent caches |
| **Deliberately stale cache with a safety backstop** | Accept staleness, then revalidate where being wrong is expensive | Scheduler snapshot is stale → kubelet re-runs admission | Client metadata is stale by construction; the backstop is the error code. `NOT_LEADER_OR_FOLLOWER` forces a metadata refresh and retry, so a client sending to the wrong broker is a latency event, not a correctness one. `FENCED_LEADER_EPOCH` plays the same role between replicas | TLB + page fault; conditional GET |
| **Assume-then-confirm** | Mutate local state before the authoritative write lands; unwind on failure | Scheduler `AssumePod`/`ForgetPod` | `QuorumController`'s pre-commit replay with `revertToSnapshot` (see §3), and the producer's optimistic batching where offsets are assigned only by the broker | Optimistic UI; write-behind caches |
| **Cache-poisoning by a cold reader** | One participant's access pattern evicts the shared working set | apiserver relist storms after restart | **The canonical Kafka incident.** One lagging consumer reading old segments pulls them into the page cache and evicts the tail every healthy consumer is reading — turning one slow client into a cluster-wide latency event. Tiered storage and follower fetching both mitigate it (Kafka [report 08](kafka-08-scale-and-operations.md)) | Buffer-pool pollution by an analytical query on an OLTP database; CDN cache churn |
| **Relist / refresh storms** | Many clients simultaneously lose their position and re-read | apiserver restart → every informer relists; mitigated by jitter, `WatchList`, APF | Controller failover → every broker's metadata catches up; a broker restart → every client refreshes metadata and reconnects, which on a TLS listener is a handshake storm on the network threads. Rebalance storms are the consumer-group form | Cache stampede on TTL expiry |

## 5. Flow control and back-pressure

| Pattern | Mechanism | In Kubernetes | In Kafka | Elsewhere |
|---|---|---|---|---|
| **Pull-based transport as structural back-pressure** | The consumer decides when to ask, so it cannot be overrun | Informers watch (push), but controllers self-pace via workqueues | **Kafka's defining choice, applied at three layers**: consumers pull, followers pull, and KRaft voters pull. No credit scheme, no flow-control frames — a slow participant simply fetches less. The cost is that liveness now depends on *fetch timeouts* (`replica.lag.time.max.ms`, `controller.quorum.fetch.timeout.ms`) rather than on send failures | gRPC flow control (push + credits) is the contrast; Reactive Streams `request(n)` |
| **Fair queuing with shuffle sharding** | Hash each flow into a random subset of queues so one heavy flow rarely collides with a light one | API Priority and Fairness: FlowSchema → PriorityLevel → shuffle-sharded queues + seats | **No equivalent — a genuine gap.** Quotas are per user / client-id / user+client-id with `<default>` fallback, enforced by throttling, not by queue isolation. One heavy client shares the same `RequestChannel` and I/O threads as everyone else. The fetch-session cache *is* sharded (8 fixed shards with per-shard eviction), but that is capacity partitioning, not fairness | AWS shuffle sharding; Linux SFQ |
| **Admission shedding before expensive work** | Reject or queue at the cheapest point | APF runs *before* authorization in the handler chain | `queued.max.requests` bounds the request queue, and a full queue makes the `Processor` **mute the channel** — back-pressure expressed as "stop reading the socket" rather than as an error. `socket.request.max.bytes` and the connection-rate limits shed earlier still | Envoy admission control; TCP SYN cookies |
| **Throttling as latency, not error** | Slow the caller down rather than failing them, so clients need no new error handling | APF queues; no explicit client-visible delay | `ClientQuotaManager` computes a delay, holds the response, and returns `throttle_time_ms` so the client self-paces. Quota exhaustion therefore shows up as a **latency cliff with no error rate** — which is why it is so often misdiagnosed (Kafka [report 06](kafka-06-broker-request-pipeline.md)) | AWS API throttling with `Retry-After`; TCP congestion control |
| **Client-side buffer with blocking back-pressure** | The producer blocks when its own buffer is full | `--kube-api-qps`/`--kube-api-burst` self-limiting | `RecordAccumulator` + `BufferPool`: `buffer.memory` bounds outstanding data and `max.block.ms` bounds how long `send()` blocks before throwing. **This is the producer's only real back-pressure**, and it is why a slow cluster surfaces first as application-thread blocking | gRPC client throttling; bounded thread-pool queues |
| **Exponential backoff with jitter** | Failures retry with growing, randomized delay | client-go `workqueue`, 5 ms → 1000 s | `retry.backoff.ms` → `retry.backoff.max.ms` with jitter (KIP-580), `reconnect.backoff.*`, and `delivery.timeout.ms` as the single wall-clock bound that subsumes them all | SQS visibility timeout; any well-behaved retry loop |
| **Event-driven completion instead of polling** | Wake a blocked item only when something that could unblock it changes | Scheduler QueueingHint replacing the 5-minute flush | **`DelayedOperationPurgatory`**: a delayed operation registers on watcher keys and is completed by the event that satisfies it (`tryComplete`), with a **hierarchical timing wheel** for timeouts — O(1) insert *and* O(1) cancel, which matters because cancellation is the common case (Kafka [report 06](kafka-06-broker-request-pipeline.md)) | epoll vs busy-wait; condition variables |

## 6. Failure detection and recovery

| Pattern | Mechanism | In Kubernetes | In Kafka | Elsewhere |
|---|---|---|---|---|
| **Lease-based liveness** | Renew frequently; absence of renewal means presumed dead | Node Lease every 10s in `kube-node-lease` | `BrokerHeartbeat` to the controller bounded by `broker.session.timeout.ms`; KRaft voter liveness by `controller.quorum.fetch.timeout.ms`; ISR membership by `replica.lag.time.max.ms`. **Three separate liveness clocks for three separate purposes** — conflating them is a common misdiagnosis | Chubby/ZooKeeper sessions; Consul TTL checks |
| **Separate heartbeat from full status** | A cheap frequent signal plus an expensive infrequent one | Node Lease (tiny, 10s) vs full Node status (large, 5m) — what made 5,000-node clusters viable | `BrokerHeartbeat` (small, frequent) vs `BrokerRegistration` (large, on start/reconnect). Identical split, same motivation: keep the frequent message O(1) in cluster size | Cassandra gossip vs full state exchange; BGP keepalives |
| **Rate-limited mass eviction** | Cap how fast a detected failure cascades | node-lifecycle controller eviction rate limits, `--large-cluster-size-threshold` | The `QuorumController` fences stale brokers **one per pass**, sampled at `sessionTimeout/8`, so a rack-wide blip cannot produce a metadata storm or a wave of leader elections (Kafka [report 03](kafka-03-kraft-controller.md)). Same instinct, much smaller mechanism | Circuit breakers; "don't let the detector cause the outage" generally |
| **Time-based membership as a weak health signal** | Membership means "recently responsive", not "actually current" | Node `Ready` can be stale relative to real capacity | **The sharpest instance in either system.** A replica is in the ISR if it fetched within `replica.lag.time.max.ms` — so "in sync" permits being arbitrarily far behind in bytes. `min.insync.replicas` counts *that* set, which is why it promises less than its name implies. KIP-966 Eligible Leader Replicas exists to close the gap; its part 2 (unclean recovery) is not in 4.3 | Any TTL-based membership; the general lesson is to check what a health signal measures |
| **Choosing unavailability over incorrectness** | Refuse to serve rather than serve wrong data, unless explicitly told otherwise | Pods stay Pending rather than being placed unsafely | A partition with no in-sync replica goes **Offline** rather than electing a stale leader. `unclean.leader.election.enable` is the explicit opt-out, and it is the only edge in Kafka that loses acknowledged writes | CP-side of CAP generally; ZooKeeper refusing writes without quorum |
| **Cooperative deletion with finalizers** | Removal blocked until every registered party acks | `deletionTimestamp` + `metadata.finalizers`; one absent party wedges everything | **No equivalent, and Kafka is better off for it.** Topic deletion is controller-driven and asynchronous: a `RemoveTopicRecord`, then brokers rename segments to `.deleted` and unlink after `log.segment.delete.delay.ms`. Nothing can veto it, so nothing can wedge it. The price is no extension point for cleanup | Terraform two-phase teardown; reference counting |

## 7. Extension and isolation

| Pattern | Mechanism | In Kubernetes | In Kafka | Elsewhere |
|---|---|---|---|---|
| **Out-of-process plugin at the trust boundary** | Third-party code runs in its own process, reached over a narrow RPC | CRI, CNI, CSI, DRA — exactly where a vendor bug would otherwise take down the control plane | **Kafka does the opposite, and pays for it.** `Authorizer`, `RemoteStorageManager`, `Partitioner`, `ReplicaSelector`, `CreateTopicPolicy`, converters and SMTs all load **in-process** in the broker or client JVM. A bad `RemoteStorageManager` takes the broker with it. The trade is latency and simplicity — a per-record out-of-process hop is not affordable on Kafka's data path, whereas Kubernetes' control path can absorb an RPC | Envoy ext_authz; PAM/NSS; browser sandboxes |
| **Sidecar / separate worker owning third-party code** | Vendor logic runs somewhere the core can survive losing | CSI sidecars translating objects into plugin calls | **Kafka Connect is exactly this pattern at cluster scale**: connector code runs in Connect workers, a separate process and separate cluster, with classloader isolation per plugin — deliberately kept out of the broker JVM (Kafka [report 07](kafka-07-streams-connect.md)) | Service mesh sidecars; the Adapter pattern |
| **Interception hooks with a declared failure policy** | Extension points that block writes must declare what happens when unavailable | Admission webhooks' `failurePolicy: Fail|Ignore`, and the classic self-gating deadlock | In-process hooks have no availability policy to declare — they cannot be "down", only wrong or slow. `StandardAuthorizer`, `CreateTopicPolicy` and `AlterConfigPolicy` are fail-closed by construction. Simpler, at the cost of no way to degrade gracefully | Circuit-breaker fallbacks; fail-open vs fail-closed auth proxies |
| **In-process policy evaluated from replicated data** | Move policy into the core and distribute it as state, not as a callout | CEL `ValidatingAdmissionPolicy` replacing many webhooks | ACLs are **metadata records** (`AccessControlEntryRecord`) replicated on `__cluster_metadata` and evaluated in-process by `StandardAuthorizer`. Same shape as CEL policy — no network hop, no availability coupling — reached by a different route: Kafka distributes the *data* rather than an expression language | eBPF replacing userspace handlers; SQL check constraints |
| **Schema-first user extension** | Users add types to the existing store rather than running a new server | CRDs with structural schemas, versioning, conversion webhooks | **No equivalent — the clearest capability gap in the comparison.** The topic is the only user-extensible object; there is no way to add a first-class type to `__cluster_metadata`. Schema Registry, which is what people reach for, is not part of Apache Kafka at all | Postgres custom types; Salesforce custom objects |

## 8. Scheduling and placement

| Pattern | Mechanism | In Kubernetes | In Kafka | Elsewhere |
|---|---|---|---|---|
| **Single-writer placement decisions over a cached view** | One process, one decision at a time, over a consistent snapshot | kube-scheduler: single-threaded scheduling cycle over a snapshot | `QuorumController`'s single-threaded event loop makes every placement decision (partition assignment, leader election, reassignment) against its timeline data structures. Same serialization instinct, and the same consequence: it is a throughput bottleneck by construction | Borg; contrast Mesos two-level offers, Omega shared-state |
| **Filter-then-score (feasibility then preference)** | Reduce to feasible candidates, then rank | Framework PreFilter/Filter → PreScore/Score | **Absent — placement is structural, not cost-based.** `StripedReplicaPlacer` stripes replicas across racks and brokers; there is no scoring, no utilisation input, no notion of a "better" broker. Everything beyond rack-striping is left to operators or Cruise Control | SQL query planning; ad retrieval + ranking |
| **Continuous rebalancing toward a goal** | A background loop moves work to improve a global objective | Descheduler (out-of-tree), Cluster Autoscaler | **No in-tree rebalancer, and this is a real gap** — Kafka will happily leave a cluster badly balanced forever. **Cruise Control** fills it externally with goal-based optimisation (rack awareness, disk, network, leader distribution) driving `AlterPartitionReassignments`. That the ecosystem's most important operational tool is out-of-tree is itself the finding (Kafka [report 08](kafka-08-scale-and-operations.md)) | Kubernetes descheduler; HDFS balancer; Cassandra `nodetool cleanup` |
| **Priority + preemption** | High-priority work displaces low-priority work | PriorityClass + DefaultPreemption, with a minimality search over victims | **Nothing.** Kafka has no workload priority concept at any layer — no per-topic or per-client priority, no preemption. Quotas throttle everyone in their class equally. Multi-tenancy is achieved by isolation and quotas, never by ranking | Borg priority bands; YARN preemption; OS nice levels |
| **Reserved-but-revocable intent** | Record an intended placement that can still be abandoned | `status.nominatedNodeName` after preemption | `addingReplicas`/`removingReplicas` during a reassignment: the target state is recorded in `PartitionRecord`, replicas catch up in the background, and the whole thing can be cancelled before it completes | Two-phase commit's prepare phase, deliberately abandonable |
| **Throttled data movement** | Bound the bandwidth a rebalance may consume so it cannot cause the outage it was meant to prevent | Not applicable — pods are recreated, not migrated | `leader.replication.throttled.rate` / `follower.replication.throttled.rate` plus per-partition `*.replicas` lists. **Reassignment without throttles is one of the most reliable ways to take down a healthy Kafka cluster** | HDFS balancer bandwidth caps; Cassandra stream throughput |

## 9. Dataplane and networking

| Pattern | Mechanism | In Kubernetes | In Kafka | Elsewhere |
|---|---|---|---|---|
| **Control plane publishes, local agent programs** | Central intent, per-node enforcement, eventually consistent | kube-proxy translating Services + EndpointSlices into dataplane rules | `MetadataLoader` replays `__cluster_metadata` → `KRaftMetadataCache` → `ReplicaManager` starts and stops `ReplicaFetcherThread`s and transitions leadership. Structurally identical, down to the eventual consistency and the lag metric | Envoy + xDS; OpenFlow controllers |
| **Full-state resync vs incremental patching** | Recompute everything and apply atomically, or send only diffs | kube-proxy's `iptables-restore` of the entire table — full state, deliberately | **Kafka went the other way, and had to.** KIP-227 incremental fetch sessions replaced full-state fetch requests precisely because per-request cost scaled with partition count. The metadata plane does both: incremental records plus periodic snapshots for new or far-behind observers. The lesson is that full-state resync is affordable only when the state is small | Envoy state-of-the-world xDS; DNS AXFR vs IXFR |
| **O(n) per-request cost as a scaling wall** | Linear cost per operation as object count grows | iptables at 10k+ Services; fixed by IPVS hashing and nftables maps | A fetch request naming every partition was O(partitions) per request per consumer — the wall KIP-227 removed by making the session sticky and sending only changes. Same wall, same class of fix: stop re-sending what has not changed | Linear ACL evaluation; the fix is always a hash, trie, or diff |
| **Sharding a large collection into bounded units** | Split one hot object into many small ones | EndpointSlice (100 endpoints each) replacing the single Endpoints object | The partition itself is the primitive form; `__consumer_offsets` at 50 partitions with group-name hashing spreads coordinator load; metadata snapshots bound observer catch-up cost | DynamoDB item limits driving fan-out |
| **Per-connection state that outlives a request** | The dataplane keeps flow state the control plane does not model | conntrack entries surviving endpoint removal — why rolling updates drop connections | **Fetch sessions**: `session_id` + epoch held broker-side across requests, evicted under cache pressure. Losing one is not a correctness problem — `SESSION_ID_NOT_FOUND` / `INVALID_FETCH_SESSION_EPOCH` force a full fetch — but at scale the eviction rate is a real and rarely-watched signal | NAT gateways; stateful firewalls; LB connection draining |
| **Kernel-bypass of the application layer** | Move bytes without copying them through user space | — | **`sendfile` zero-copy** from page cache to socket is Kafka's single largest performance mechanism, and it is silently forfeited by TLS, by a tiered fetch, and historically by format down-conversion. Knowing what defeats it is worth more than knowing it exists (Kafka [report 01](kafka-01-log-storage.md)) | nginx `sendfile`; io_uring; DPDK; RDMA |

## 10. Resource management

| Pattern | Mechanism | In Kubernetes | In Kafka | Elsewhere |
|---|---|---|---|---|
| **Request/limit split** | One number for admission and share allocation, another for enforcement | requests → scheduling and `cpu.weight`; limits → CFS quota and OOM kill | **Nothing.** Kafka has no resource model for its own workloads — a topic does not request memory or CPU. Quotas bound *rate*, not allocation, and there is no admission control on topic creation beyond policy plugins | Borg requested vs limit; JVM `-Xms`/`-Xmx` |
| **Service classes derived from usage shape** | Derive a tier from the resource relationship rather than a separate field | Guaranteed / Burstable / BestEffort, driving cgroups and `oom_score_adj` | The quota **hierarchy** is the nearest analogue: user+client-id > user > client-id, each with a `<default>` fallback, resolved most-specific-first. It classifies *callers*, not workloads | Diffserv; storage tiers |
| **Local pressure eviction ranked by contract** | The node sheds load itself, worst-behaved tenant first | kubelet eviction manager: rank by QoS, then usage over request | **No ranking at all** — retention deletes the *oldest data*, never the least-deserving tenant, and it runs continuously rather than under pressure. If disk fills anyway, the log dir goes offline and takes every partition on it. Fairness is expected to come from quotas upstream, not from shedding | Linux OOM score; RPC load shedding |
| **Reactive autoscaling with damping** | Ratio-based target tracking plus a stabilisation window | HPA with 10% tolerance and 300s scale-down stabilisation | **Kafka does not autoscale, at all.** Brokers are added manually and partitions must be reassigned explicitly; partition count can only increase, and increasing it *breaks key-based ordering* for existing keys. This irreversibility is the single most consequential difference from an elastic system | AWS target tracking; thermostat loops |
| **Safety interlock on voluntary operations** | Operations must ask permission; involuntary failures ignore it | PDBs enforced by the Eviction API, ignored by node-pressure eviction and raw DELETE | `min.insync.replicas` is the closest, and it interlocks **writes** rather than operations — producers fail with `NotEnoughReplicas` when durability cannot be met. Controlled shutdown moves leadership before stopping, and KIP-1066 `cordoned.log.dirs` (new in 4.3) finally adds a "drain this thing" primitive | Maintenance windows; Cassandra `nodetool drain` |
| **Cost dominated by an invisible axis** | The dominant cost is not the resource operators think they are buying | Cluster cost is nodes; the hidden axis is control-plane scale | **Cross-AZ network, not disk or compute.** Replication crosses AZs by construction and is billed in both directions, so a durability decision is a line item. KIP-392 follower fetching and tiered storage are both, in practice, cost levers before they are performance ones (Kafka [report 08](kafka-08-scale-and-operations.md)) | Cross-region egress in any cloud architecture |

## 11. Patterns Kafka contributes that Kubernetes does not exhibit

New rows for future systems to be compared against, drawn from the Kafka series.

| Pattern | Mechanism | In Kafka | Elsewhere |
|---|---|---|---|
| **Batch as a cross-layer primitive** | The unit of batching is preserved end to end rather than repacked at each hop | The `ProducerBatch` is the unit of compression, of the CRC, of idempotent sequencing, of the disk write, and of replication — the broker does not unpack it. This is why *client* tuning moves *broker* CPU and disk metrics | Nagle's algorithm; group commit in databases; GraphQL query batching |
| **Ordering as a partitioning decision made once** | Total order within a shard, none across shards, fixed at write time and unchangeable | The partition key determines ordering forever; changing partition count breaks key→partition stability, and there is no online repartitioning. Nearly every hard Kafka design question reduces to this one irreversible choice | Sharded databases with a fixed hash ring; Kinesis shards |
| **Consumption as a cursor, not a removal** | Reading does not mutate shared state, so fan-out is free and replay is trivial | Offsets are held by the consumer and committed as ordinary records; the broker keeps no per-consumer data-path state. Every queue feature Kafka lacks is a direct cost of this, which is why KIP-932 share groups needed a whole new subsystem to reintroduce per-record acknowledgement | Event sourcing; CDC log readers; contrast SQS/RabbitMQ |
| **The same protocol at every layer** | One RPC and one log implementation reused for client reads, replication, and consensus | `Fetch` serves consumers, followers, and KRaft voters alike, reusing one batching, back-pressure, indexing and zero-copy path. The cost is that consensus inherits fetch-interval latency and needs pre-vote to stay stable | Unix "everything is a file"; contrast systems with separate control and data protocols |

## Open questions to revisit as more systems are added

Two of the previous four are now **answered** by the Kafka series; they are kept with their resolutions because the reasoning is the useful part.

- **~~Where does "level-triggered wins" hold, and where does it fail?~~ Answered: the boundary is exactly control plane vs data plane.** Level-triggered reconciliation requires cheap full-state reads. Kafka uses it in the control plane (brokers reconcile against the replayed metadata log) and cannot use it in the data plane, because "reconcile to current state" would mean skipping records — and because the state is days of data on disk, not an object in RAM. The generalisation: use level-triggered wherever the desired state is small and re-readable, edge-triggered wherever history itself is the payload.
- **~~Fencing tokens — is Kubernetes the outlier?~~ Answered: yes, and Kafka is the clean counter-example.** Kafka validates leader epoch, partition epoch and producer epoch *at the guarded resource*, so a stalled leader that wakes up is rejected. Kubernetes deliberately relies on idempotent reconciliation instead. The precise class of side effect that makes the absence unacceptable is now statable: **any effect that is not idempotent and not observable in the state being reconciled** — an external billing call, a cloud API mutation, or, in Kafka's case, an append to a shared log where a duplicate write is indistinguishable from a legitimate one. Compare against Chubby and HDFS when those reports exist.
- **Single Raft group vs sharded consensus.** Kafka now provides a middle data point: one Raft group for metadata, per-partition leader/ISR replication for data, with the hot path never crossing the consensus group. Still open: quantify this against Spanner's per-split Paxos and CockroachDB's range leases, and characterise when a hybrid beats uniform sharding.
- **B+tree vs LSM vs append-only for a metadata store.** etcd chose bbolt; Kafka chose an append-only log plus periodic snapshots, deliberately avoiding compaction pauses. Compare against ZooKeeper (in-memory + snapshots) and TiKV (RocksDB) on read latency, write amplification and recovery time.
- **New: what is the right home for third-party code?** Kubernetes pushes it out of process at every trust boundary (CRI/CNI/CSI); Kafka loads it in-process and isolates only at the Connect worker. Both are defensible under their own latency budgets. Revisit when a system with per-record extension on a hot path (Envoy/WASM, eBPF) is deep-dived, and try to state the latency threshold at which in-process becomes mandatory.
- **New: which systems can be rebalanced, and which merely can be re-placed?** Kubernetes recreates pods; Kafka must *move bytes*, so its rebalancing is throttled, slow, and out-of-tree. Systems that store state have a fundamentally harder placement problem than systems that schedule stateless work — worth characterising precisely when Spanner, Cassandra or HDFS is added.
